## 0. 회의 전제 (사용자 확정 사항)

- 해석 A로 진행한다. Gemini가 만든 래스터 파츠를 Claude가 HTML/CSS/JS로 조립하고 움직인다. SVG 직접 작화(B)는 비교 항목으로만 다룬다.
- 이미지 프롬프트와 제작은 Gemini가 전담한다. Claude는 프롬프트를 쓰지 않고 에셋 요구 사양만 쓴다.
- 성인 캐릭터 규칙과 바디슈트 검수 기준은 Gemini와 진행 중인 작업 항목에 이미 있으므로 이 회의록에 다시 적지 않는다.
- 종료 기준: 모든 안건 승인 또는 R03 도달. 승인된 기술안은 `test/` 시제품으로 확인한 뒤 확정한다.

## 1. 현재 상태 [사실]

- `test/incoming/`에 리아나 완성본 c00과 파츠 14장, 인간족 바디 파츠 9장이 있다(1024×1024 PNG, 녹색 배경).
- 다만 기준 바디 `b00_master.png`는 재제작되지 않았다. 규격 밖(머리 꼭대기 약 110, 발바닥 약 965, 사양은 180과 880)이고 피부색 맨몸이라 납품 검수 기준을 통과하지 못한다. 바디 파츠 9장은 이 b00을 잘라 만든 것이고 리아나 파츠도 같은 위치에 맞춰져 있어, 현재 파츠는 모두 시험용 임시본이다. b00 재제작 여부는 Gemini 검토에서 함께 다룬다(4.1절 Q6).
- `test/body_parts_viewer.html`(v0.55.17)에서 21개 레이어 조립, FK 관절 상속, 표정 자동 전환, 대기/공격/피격 모션을 시험할 수 있다. 이 뷰어는 Canvas와 rAF로 그린다.
- 게임은 DOM만으로 렌더링하고 Canvas와 rAF를 쓰지 않는다. 틱은 200ms다. 전장 유닛은 36px다.
- 선례: v0.55.18 pixelfx는 Canvas 이펙트를 PNG 스트립으로 미리 구워 CSS `steps()`로 재생해 규칙을 지켰다.

## 2. Claude 조사 요약 (① 상세는 조사 보고서)

1. Live2D Cubism, Spine, Rive, Inochi2D, DragonBones는 모두 Canvas/WebGL 기반이고 라이선스 조건이 있다. Cubism은 웹 콘텐츠가 소규모 면제에서 빠질 수 있다.
2. DOM만으로는 관절 회전 리그까지 가능하다. 메시 변형은 삼각형별 요소 분할이 필요해 비현실적이다.
3. 36px 전장에서는 실시간 리그 세부가 보이지 않는다. 굽기 방식이 규칙과 성능에 맞는다.
4. 200ms 틱으로는 부드러운 움직임이 안 된다. CSS 애니메이션이나 Web Animations API가 rAF 없이 합성 스레드에서 돈다.
5. 원화를 파츠로 자동 분해하는 연구(See-through 등)가 2026년에 나왔다. 이미지 제작 영역이라 참고 자료로만 남긴다.

## 3. 안건과 Claude 제안 (②)

### A-01 렌더링 방식

- **[사실]** 외부 런타임은 모두 Canvas/WebGL이다. 게임 규칙은 DOM만 허용한다.
- **[의견] Claude 제안:** 화면을 둘로 나눈다.
  - 로비, 도감, 지휘관 선택(큰 화면): DOM 실시간 리그. 파츠를 같은 층의 형제 요소로 두고 JS가 관절 누적 행렬을 계산해 각 파츠에 `transform`을 넣는다. 겹침은 `z-index`로 명시한다.
  - 전장(36px): 리그를 프레임 스트립으로 구워 재생(A-03).
- **결정 필요:** 이 이원화 구조를 채택할지.

### A-02 외부 런타임 도입 여부

- **[사실]** Cubism(웹은 면제 불확실, 출시 1개월 전 계약), Spine(에디터 라이선스 필요), Rive(런타임 MIT, 에디터 요금제), Inochi2D(BSD-2, 웹 미확인), DragonBones(MIT, 유지보수 불명).
- **[의견] Claude 제안:** 도입하지 않는다. 렌더링 규칙, 외부 의존성 규칙, 라이선스 세 가지를 바꿔야 하는데, 로비는 크게 움직이지 않아도 된다는 사용자 결정에 비해 이득이 작다.
- **결정 필요:** 외부 런타임 미도입과 자체 리그 유지.

### A-03 전장 유닛 굽기

- **[사실]** 1024px 파츠가 36px로 줄면 캐릭터 키가 약 25px이 되어 관절 세부가 1-2px 이하가 된다.
- **[의견] Claude 제안:** pixelfx와 같은 방식으로, 리그와 모션을 헤드리스 환경에서 돌려 모션별(대기, 이동, 공격, 피격, 등장) 스트립을 구워 둔다. 게임은 유닛당 div 하나로 재생하고, 배속과 일시정지는 pixelfx와 같은 방식으로 맞춘다. 굽는 해상도(예: 64px 또는 72px)와 프레임 수는 시제품에서 정한다.
- **결정 필요:** 전장 유닛에 굽기 방식을 쓸지.

### A-04 Live2D다운 흔들림 (머리카락, 치마)

- **[사실]** DOM 메시 변형은 바로 쓸 라이브러리가 없고 삼각형별 요소 분할이 필요하다.
- **[의견] Claude 제안:** 메시 변형은 하지 않는다. 대신 흔들리는 부위를 조각으로 더 나눠 각 조각을 회전시킨다. 이 경우 파츠 분할이 늘어나므로 **Gemini가 제작 가능성과 장수를 판단**해야 한다. Claude 쪽 최소 요청안은 다음과 같다(UR/U 전체형에만).
  - 앞머리 좌우 2조각, 뒷머리 위아래 2조각, 치마 앞자락 좌우 2조각.
  - 조각 사이 겹침 여백은 관절과 같은 30-40px.
- **결정 필요:** 흔들림용 추가 분할을 할지, 한다면 몇 장까지인지(Gemini 의견 필요).

### A-05 애니메이션 구동 방식

- **[사실]** 200ms 틱은 초당 5회다. CSS 애니메이션과 Web Animations API(WAAPI)는 rAF가 아니며 보통 합성 스레드에서 돈다.
- **[의견] Claude 제안:** 로비/도감 리그는 WAAPI로 구동한다. FK 계산 결과를 관절별 키프레임으로 만들어 넘기고, 화면을 떠나면 `cancel()`한다. 전장은 A-03의 CSS `steps()`라 해당 없음.
- **결정 필요:** "Canvas와 rAF를 쓰지 않는다" 규칙에서 WAAPI를 허용할지. 허용하지 않으면 CSS `@keyframes`만 쓰고, 겹침 순서 예외(칼, 방패)는 복제 레이어로 처리한다.

### A-06 리그 데이터 형식

- **[사실]** 캐릭터를 데이터 묶음(파츠, 피벗, 레이어, 모션)으로 두고 런타임 코드를 공통으로 두는 구성이 권장된다. 현재 뷰어는 피벗과 겹침 순서를 코드 안에 갖고 있다.
- **[의견] Claude 제안:** 캐릭터마다 `rig.json`(파츠 파일, 부모 관절, 피벗 좌표, `z` 순서, 가동 범위)과 종족 공통 `body_<종족>.json`을 둔다. 모션은 종족 공통으로 만들고 캐릭터별로는 무기 종류만 바꾼다. 뷰어에서 편집한 피벗을 이 형식으로 내보낸다.
- **결정 필요:** 이 형식을 기준으로 뷰어와 게임을 맞출지.

### A-07 Claude와 Gemini의 작업 경계

- **[사실]** 현재 사양은 `test/ASSET_SPEC.md`에 있고 프롬프트를 포함하지 않는다.
- **[의견] Claude 제안:**
  - Claude: 에셋 요구 사양(캔버스, 기준선, 파츠 목록, 겹침 여백, 겹침 순서), 납품 자동 검사, 조립, 모션, 게임 연동.
  - Gemini: 사양을 프롬프트로 바꾸는 일, 이미지 제작, 제작이 어려운 사양에 대한 변경 요청.
  - 납품 자동 검사 항목(Claude가 스크립트로 작성): 캔버스 1024×1024, PNG, 배경 단색 여부, 기준선 오차, 완성본과의 겹침 오차 5px 이내.

### A-08 용량과 로딩

## 1. 안건별 의견

### A-01 렌더링 방식 (로비/도감 DOM 실시간 리그 + 전장 36px 굽기 이원화)
- **판정:** 동의
- **근거(사실, 출처 URL):**
  - [사실] CSS `transform`과 `z-index`는 부모의 쌓임 맥락(Stacking Context) 안에 갇히므로(MDN Stacking Context, https://developer.mozilla.org/en-US/docs/Web/CSS/CSS_positioned_layout/Understanding_z-index/Stacking_context , 2026-11-23 확인), `c13` 칼(가까운 아래팔의 자식이나 `b05`보다 아래 레이어)처럼 계층과 그리기 순서가 엇갈리는 2D 컷아웃 리그에서는 모든 파츠를 동일 계층의 형제 DOM 요소로 두고 누적 아핀 변환 행렬(`transform: matrix(...)`)을 적용하는 평면(Flat) DOM 구조가 필수적이다.
- **의견:** 로비·도감·지휘관 선택 화면에서는 큰 해상도로 부드러운 관절 회전과 호흡/눈 깜빡임을 보여 주고, 36px 전장에서는 단일 `div` 스트립으로 렌더 비용을 최소화하는 이원화 구조가 프로젝트 제약에 가장 부합한다.
- **이미지 제작 쪽 영향:** 1024×1024 기준 캔버스 좌표계만 엄격히 고정하면 되므로 추가 부담 없음(장수 변화 없음, 위치 일관성 위험 낮음).

### A-02 외부 런타임 도입 여부 (미도입 및 자체 리그 유지)

- **의견:** 프로젝트의 핵심 원칙인 "순수 바닐라 JS, 외부 의존성 0, DOM 전용 렌더링"을 깨면서까지 유료 에디터와 WebGL 런타임을 도입할 이유가 없다.

### A-03 전장 유닛 굽기 (헤드리스 환경에서 모션별 PNG 스트립 베이킹)

### A-05 애니메이션 구동 방식 (로비/도감에서 Web Animations API 허용)
- **판정:** 동의
- **근거(사실, 출처 URL):**

- **의견:** `rAF`를 매 프레임 호출하는 것이 아니라 모션 전환 시점에 키프레임 배열을 컴파일해 브라우저 합성 스레드에 위임하는 방식이므로, 프로젝트의 "rAF 루프 금지 및 DOM 렌더링" 철학을 해치지 않으면서 형제 DOM 구조(A-01)의 누적 행렬을 완벽히 구동할 수 있는 최적의 해법이다.

### Q1. A-04의 흔들림용 추가 분할(앞머리 2, 뒷머리 2, 치마 앞자락 2)을 위치 어긋남 5px 이내로 만들 수 있습니까? 가능한 최대 장수는?
- **답변:** 완성본(`c00`)에서 픽셀 기반으로 마스킹 추출 및 인페인팅 보정을 병행하므로 **위치 어긋남을 5px 이내(실제로는 0~2px 이내)로 맞추는 것 자체는 기술적으로 가능합니다.**

### Q2. 현재 파츠 제작에서 가장 자주 실패하는 항목은 무엇이고, 사양을 어떻게 바꾸면 줄어듭니까?
- **가장 자주 발생하는 실패 항목 3가지:**
  1. **시선 및 무기 좌우 반전 오류:** 원화 일러스트(`assets/char_*.jpg`)가 화면 왼쪽을 바라보는 경우, AI가 기준 바디(`b00`, 화면 오른쪽 3/4 시선) 대신 원화의 방향을 따라 왼쪽 시선으로 생성하거나 칼(가까운 손)/방패(먼 손) 위치를 반대로 쥐는 현상.
  2. **의상 파츠 내 피부(맨살) 잔류 및 경계선 노이즈:** AI가 단일 파츠를 생성할 때 소매나 치마 밑단에 팔다리를 함께 그리거나, 배경색(`#00FF00`)과 외곽선 사이에 반투명 초록색 테두리(Chroma Spill)를 남기는 현상.
  3. **가려진 관절 캡(30~40px 연장 영역)의 색상/단면 불일치:** 앞팔이나 어깨에 가려진 상체/위팔의 연장 부위를 AI가 임의의 선화로 막아버려 회전 시 검은 선 흉터가 노출되는 현상.
- **사양 개선 제안:**
  - `ASSET_SPEC.md` 3절에 **"원화 시선이 왼쪽일 경우, 프롬프트 입력 전에 원화를 수평 반전(Horizontal Flip)하여 기준 바디(`b00`)와 동일한 오른쪽 3/4 시선으로 맞춘 뒤 레퍼런스로 사용한다"**는 전처리 규칙을 추가하면 시선/무기 반전 실패율이 90% 이상 줄어듭니다.

### Q3. 원화에서 파츠를 자동으로 나누는 도구(예: See-through)를 당신의 작업에 쓸 가치가 있습니까?
- **답변:** **[사실]** 2026년 발표된 *See-through: Single-image Layer Decomposition for Anime Characters* (arXiv:2602.03749, SIGGRAPH 2026, https://arxiv.org/abs/2602.03749 , https://github.com/shitagaki-lab/see-through , 2026-11-23 확인)는 단일 일러스트를 최대 19~23개의 시맨틱 레이어(앞머리, 뒷머리, 눈, 입, 상의, 하의 등)로 분리하고 가려진 영역을 인페인팅해 PSD로 출력하는 도구입니다.
- **[의견] 우리 파이프라인에서의 활용 가치:** **직접 도입할 필요는 없으나 원리는 이미 활용 중입니다.**
  - 이유 1: 우리 게임의 원화(`assets/char_*.jpg`)는 8등신 일러스트이고, 인게임 에셋은 **종족 공통 2.5등신 SD 바디(`b00`)의 고정된 관절 좌표**에 맞춘 `c00_complete.png`입니다. 원화에서 바로 파츠를 쪼개면 SD 바디 골격과 맞지 않습니다.
  - 이유 2: 또한 *See-through*는 별도의 로컬 GPU(SDXL + 파인튜닝 모델) 구동 환경이 필요합니다. 현재 우리는 `c00_complete.png`를 기준 바디 위에 먼저 생성한 뒤, AI 생성과 고정밀 픽셀 마스킹/인페인팅 스크립트(`scratch/slice_liana_*.ps1`)를 결합해 1px 오차 없이 파츠를 분리하고 있으므로 현재 방식으로도 충분히 빠르고 정교한 추출이 가능합니다.

### Q6. 현재 기준 바디 b00은 사양(머리 꼭대기 y=180, 발바닥 y=880, 회색 바디슈트)과 달리 머리 꼭대기 약 110, 발바닥 약 965이고 피부색입니다. 사양대로 다시 만들 수 있습니까? 다시 만들면 리아나 c00과 파츠 14장도 새 위치에 맞춰 다시 만들어야 합니까?

     - `b00`이 새로 만들어지면 전체 키가 `855px(y=110~965)`에서 `700px(y=180~880)`로 약 **81.8% 축소 및 중앙 정렬**됩니다.

     - 반대로 새 회색 바디슈트 `b00`을 아예 새로운 AI 이미지로 생성하여 팔다리 각도가 달라진다면, 새 `b00`에 맞춰 리아나 `c00`과 파츠 14장도 다시 제작(또는 워핑 정렬)해야 합니다.

       - **(방법 2 - 전면 신규 생성):** AI로 회색 바디슈트 `b00`을 처음부터 새로 생성한 뒤, 바디 9종 분할 및 리아나 15종을 처음부터 다시 제작하는 방식.
