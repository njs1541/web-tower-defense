# R01 조사 보고서: HTML 기반 Live2D식 캐릭터 연출을 게임에 적용하는 방식

- 작성: Claude (Opus 5.5)
- 조사일: 2026-11-23
- 대상 버전: v0.55.19
- 범위: 해석 A. Gemini가 만든 래스터 파츠를 Claude가 HTML/CSS/JS로 조립하고 움직인다. SVG 직접 작화(B)는 비교용으로만 다룬다.
- 표기: **[사실]** 출처나 코드로 확인한 내용. **[의견]** Claude의 판단. 신뢰도는 높음/중간/낮음으로 적는다.

---

## 1. 요약

1. **외부 Live2D식 런타임(Cubism, Spine, Rive, Inochi2D, DragonBones)은 모두 Canvas나 WebGL로 그린다.** 프로젝트의 "DOM 렌더링만" 규칙을 바꾸지 않는 한 그대로 쓸 수 없다. 라이선스 조건도 저마다 있다(2절).
2. **DOM만으로 할 수 있는 것은 "계층형 파츠 회전 리그"까지다.** div를 관절마다 중첩하고 `transform-origin`을 관절 위치에 두면 자식 파츠가 부모를 따라 움직인다. 현재 `test/` 파츠 분할(바디 9장 + 의상 14장)은 이 방식에 바로 맞는다(3절).
3. **Live2D의 핵심인 메시 변형은 DOM에서 사실상 비현실적이다.** 삼각형마다 요소를 하나씩 만들어 잘라내고 행렬을 거는 방법뿐이며, 바로 쓸 라이브러리가 없다(3.3절).
4. **전장 유닛은 36px라서 실시간 리그의 세부가 보이지 않는다.** pixelfx 도입(v0.55.18) 때처럼 리그를 미리 프레임 스트립으로 구워 CSS `steps()`로 재생하는 방식이 규칙과 성능 모두에 맞다(4절).
5. **애니메이션 구동 방식은 사용자 결정이 필요하다.** 게임 틱은 200ms라 부드러운 움직임에 쓸 수 없다. CSS `@keyframes`나 Web Animations API는 rAF를 쓰지 않으면서 합성 스레드에서 돈다. 이것을 규칙상 허용할지 정해야 한다(5절).

## 2. 외부 런타임 조사

| DragonBones (DragonBonesJS) | PixiJS/Egret | MIT. 유지보수 여부 불명 | 맞지 않음. 유지보수 위험 | 낮음 |

Expandable Application은 사용자 파일로 모델을 늘리는 서비스나 여러 작품을 묶은 포털을 뜻하며, 웹 앱은 별도 플랜 분기다. 연매출 1천만 엔 미만은 출판 라이선스가 면제되고, Cubism Editor FREE도 이 규모면 상업용으로 쓸 수 있다(기능 제한 있음). 출처: https://www.live2d.com/en/sdk/license/expandable/ , https://www.live2d.com/en/cubism/comparison/ . 결론(미도입)은 렌더링 규칙 때문에 그대로다.

**[사실]** 위 런타임은 모두 Canvas 또는 WebGL을 쓴다. CLAUDE.md는 "렌더링은 전부 DOM이다. Canvas와 rAF는 쓰지 않는다"고 정하고 있다.
**[의견]** 런타임을 도입하면 외부 의존성 규칙(첫 예외), 렌더링 규칙, 라이선스 세 가지를 동시에 바꿔야 한다. 그만큼 이득이 큰 곳은 로비 일러스트 연출 정도인데, 사용자는 "로비는 크게 움직이지 않아도 된다"고 정했다. 도입하지 않기를 권한다(신뢰도 높음).

## 3. DOM 기반 자체 리그

### 3.1 계층형 회전 리그 (권장 기본안)

**[사실]** 일반적인 방식은 다음과 같다.
- 관절마다 위치를 잡은 요소를 두고 `transform-origin`을 관절 좌표에 맞춘다. 부모를 회전하면 자식이 따라 움직인다.
- 2D 컷아웃 애니메이션에서는 자식이 부모 위에 그려지므로, 겹침 순서는 소스 순서에 맡기지 말고 `z-index`로 명시한다.
- 캐릭터를 "데이터 묶음(파츠, 피벗, 레이어, 제약)"으로 만들고 런타임 코드는 공통으로 두는 구성이 권장된다.

**[사실, 프로젝트]** `test/ASSET_SPEC.md` 6절의 겹침 순서는 "먼 팔 → 몸통 → 가까운 팔"처럼 계층과 겹침이 엇갈린다. 예를 들어 `c13` 칼은 가까운 아래팔의 자식이지만 `b05` 가까운 아래팔보다 아래에 그려야 한다. 중첩 div 안에서는 `z-index`가 부모의 쌓임 맥락에 갇히므로, **계층(변환 상속)과 겹침(그리기 순서)을 분리하는 구조**가 필요하다.

**[의견]** 해결책은 두 가지다.
- (가) 모든 파츠를 같은 층의 형제 요소로 두고, JS가 관절 체인의 누적 행렬을 계산해 각 파츠에 `transform: matrix(...)`를 직접 넣는다. 겹침은 `z-index`로 자유롭게 정한다. 현재 Canvas 뷰어의 FK 계산을 그대로 옮길 수 있다.
- (나) CSS 중첩만 쓰고 겹침이 어긋나는 파츠(칼, 방패)만 복제 레이어로 처리한다. 코드는 적지만 예외가 캐릭터마다 늘어난다.
- (가)를 권한다. 매 프레임 JS가 필요하므로 5절의 구동 방식과 묶어서 정한다.

### 3.2 현재 뷰어와의 차이

**[사실, 프로젝트]** `test/body_parts_viewer.html`(v0.55.17)은 Canvas 렌더링과 `requestAnimationFrame`, `getImageData`(관절 끝 자동 연장)를 쓴다. 시험 도구라서 규칙 위반은 아니지만 **그대로 게임에 옮길 수는 없다.** 게임에 연동하려면 다음 중 하나가 필요하다.
1. DOM 렌더러로 다시 작성한다(3.1 (가)).
2. 뷰어를 "굽기 도구"로 쓰고 게임은 결과 이미지만 재생한다(4절).

관절 끝 자동 연장은 픽셀을 다루므로 DOM에서는 실시간으로 할 수 없다. 미리 파츠 PNG에 적용해 두는 전처리로 옮겨야 한다.

### 3.3 메시 변형

**[사실]** DOM만으로 이미지를 휘게 하려면 삼각형마다 요소를 하나씩 만들어 잘라내고(`clip-path` 또는 그라데이션 마스크), 삼각형별 아핀 행렬(`matrix`/`matrix3d`)을 걸어야 한다. 네 점 대응으로 `matrix3d`를 푸는 예제와 dom3d 기법은 있지만, 이미지 메시 변형을 DOM만으로 하는 완성 라이브러리는 찾지 못했다(신뢰도 중간).
**[의견]** 머리카락이나 치마 흔들림 같은 Live2D다운 효과는 메시 대신 **파츠를 더 잘게 나누고 각 조각을 회전**하는 방식으로 근사한다. 이 경우 파츠 분할은 Gemini의 제작 범위가 늘어나는 문제이므로 회의 안건으로 올린다(회의록 A-04).

## 4. 전장 36px 유닛

**[사실, 프로젝트]** 전장 유닛은 36px이고(style.css 3978-3979), 파츠 캔버스는 1024px다. 약 1/28로 줄어들어 캐릭터 전체 키(700px)가 화면에서 약 25px이 된다. 눈 깜빡임이나 손가락 같은 세부는 1-2px 이하가 된다.
**[사실]** 엔진들은 골격 애니메이션을 미리 텍스처나 프레임으로 굽는 방식을 제공하고, 화면에 캐릭터가 많을수록 굽는 쪽이 프레임당 비용이 낮다. 대신 메모리를 더 쓰고 프레임 수가 고정된다(Cocos Creator 문서, Unity 사례).
**[사실, 프로젝트 선례]** v0.55.18 pixelfx는 Canvas 런타임을 게임에 싣지 않고 `scratch/build_pixel_fx.mjs`로 PNG 스트립을 구워 CSS `steps()`로 재생한다. 배속은 `gameSpeed`로 나누고 일시정지는 `body.game-paused`로 멈춘다.
**[의견]** 전장용은 같은 방식을 권한다. 리그와 모션을 Node 또는 헤드리스 Edge에서 돌려 모션별(대기, 이동, 공격, 피격, 등장) 프레임 스트립을 64px이나 72px 정도로 굽고, 게임은 div 하나로 재생한다. 규칙 변경이 필요 없고 DOM 요소 수도 유닛당 1개로 유지된다(신뢰도 높음). 실시간 DOM 리그는 크게 보여 주는 로비, 도감, 지휘관 선택 화면에만 쓴다.

## 5. 애니메이션 구동 방식

**[사실]** `transform`과 `opacity`의 CSS 애니메이션과 Web Animations API는 보통 합성 스레드에서 돌아서 메인 스레드가 바빠도 부드럽다. `setInterval`은 한 프레임에 두 번 갱신하거나 갱신을 건너뛸 수 있어 프레임 단위 애니메이션에 가장 약하다(MDN, web.dev).
**[사실, 프로젝트]** 게임은 소환 1000ms, 틱 200ms의 `setInterval` 두 개로 돌고 틱마다 400칸을 다시 그린다. 200ms는 초당 5회라 관절 애니메이션에 쓸 수 없다.

선택지는 다음과 같다.

| 안 | 내용 | 규칙과의 관계 |
|---|---|---|
| (1) CSS `@keyframes`만 | 모션을 키프레임으로 미리 정의. 3.1 (나) 구조와 맞음 | 규칙 변경 없음 |
| (2) Web Animations API | JS에서 키프레임을 만들어 재생. 배속은 `playbackRate`, 일시정지는 `pause()` | rAF는 아니지만 "JS 애니메이션"이라 허용 여부를 정해야 함 |
| (3) 화면 한정 rAF | 로비/도감 리그 화면에서만 rAF로 FK 계산 | "rAF 금지" 규칙의 예외가 됨 |
| (4) 굽기 | 전장용. 4절 | 규칙 변경 없음 |

**[의견]** 전장은 (4), 로비/도감은 (2)를 권한다. (2)는 rAF 없이 3.1 (가)의 계산 결과를 관절별 키프레임으로 넘길 수 있고, 배속과 일시정지를 API로 제어할 수 있다. (3)이 가장 단순하지만 규칙 예외가 된다(신뢰도 중간).

## 6. 파츠 생성 쪽 동향 (Gemini 담당 영역, 참고만)

**[사실]** 원화 한 장을 의미 단위 RGBA 레이어로 나누고 가려진 부분을 채우는 연구가 2026년에 나왔다. See-through(arXiv 2602.03749)는 SDXL 기반 모델, 애니메 깊이 모델, 신체 분할을 조합한다. 저자들은 리깅은 다루지 않는다고 밝혔다. 같은 계열로 Live2D 분류 체계를 쓰는 연구(arXiv 2607.27348로 표시, 초록만 확인해 세부는 검증 못 함)와 상용 레이어 분리 도구가 있다.
**[의견]** 이미지 제작은 Gemini 담당이므로 Claude는 도입을 제안하지 않는다. 다만 "파츠를 새로 그리게 하기보다 기준 이미지에서 해당 부위만 남기는 편집"(ASSET_SPEC.md 3절)과 같은 문제를 다루므로, Gemini가 자기 작업에 참고할지 판단할 자료로 회의록에 남긴다.

## 7. B안(SVG 직접 작화) 비교

**[사실]** LLM은 깜빡임, 흔들림, 부품 회전 같은 단순 SVG/CSS 애니메이션은 만들 수 있지만, 형태가 휘는 유기적인 움직임은 일반 LLM 전반에서 약하다고 보고된다(VAnim, ICML 2026). Claude가 HTML/CSS 변환에 쓰인 연구(Decomate)는 있으나 캐릭터 품질을 비교한 자료는 찾지 못했다.
**[사실, 프로젝트]** 현재 원화 21명 중 19명은 이미 절차적 SVG나 자동 추론으로 렌더링되고 있다(CLAUDE.md "캐릭터별 현황").
**[의견]** B안은 이미지 제작을 Claude가 일부 맡게 되어 역할 분담과 부딪히고, 원화 품질을 따라가기도 어렵다. 채택하지 않는다. 기존 절차적 SVG는 파츠가 없는 캐릭터의 대체 렌더링으로만 둔다.

## 8. 용량

**[사실, 프로젝트]** 리아나 파츠 14장(1024×1024 PNG, 녹색 배경)은 2.8MB, 바디 9장을 더하면 4.4MB다.
**[의견]** 출시 45명을 원본 그대로 두면 캐릭터 파츠만 약 120MB 이상이 된다. 배경 제거 후 내용 영역 트림, WebP 변환, 캐릭터별 아틀라스로 줄여야 한다. 도감은 정지 이미지 목록과 선택 시 지연 로딩으로 정해져 있으므로(사용자 결정), 첫 로딩에는 썸네일만 들어간다. 압축 목표치는 시제품에서 측정해 정한다.
